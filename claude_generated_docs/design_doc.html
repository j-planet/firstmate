Firstmate Design Guide

Firstmate turns one coding-agent session into a supervisor that runs a crew of other coding agents in parallel. This guide explains how the pieces fit, where each major component lives, and why it was built the way it was. It assumes solid software engineering and zero prior knowledge of this repo.

§1The short version

  • One human talks to one agent. The human (the captain) chats only with the first mate. The first mate never edits project code. It hands each task to a worker agent (a crewmate) that runs in its own terminal window and its own git worktree.
  • The repository itself is the product. There is no app to install. Launching Claude Code, Codex, Pi, or another supported agent CLI inside this repo turns that session into the first mate, because the CLI reads AGENTS.md and follows it.
  • Judgment goes to the model, mechanics go to bash. Waiting, polling, classifying events, locking, merging, and cleanup are deterministic scripts in bin/. The model spends tokens only when something needs a decision.
  • Everything that matters is on disk. Task records, append-only status logs, and a durable wake queue mean any session can die and the next one picks up exactly where it left off.
  • Authority is explicit. Merging, discarding work, and anything destructive need the captain's word. Scripts refuse rather than guess, and every refusal names what is missing.

§3Design principles

VISION.md is 78 lines and worth reading in full. Each of its principles shows up as concrete code decisions, which is the fastest way to understand why the code looks the way it does.

PrincipleWhat it meansWhere it shows up in the code
One captain, one interface Workers never address the human. The first mate turns internal state into outcomes, consequences, and decisions. AGENTS.md §9 lists internal terms (worktree, watcher, task id) that must be translated before they reach chat. Worker briefs route every question through status lines.
Authority is explicit, never inferred The human is the default authority for every gate. Autonomy exists only as an opt-in grant, scoped per project. --mode and --yolo are required on every ship spawn. fm-pr-merge.sh refuses red or unverified PRs. Standing merge autonomy is a +yolo flag in data/projects.md.
Scripts own the mechanics, agents own the judgment Anything that can be exact runs in bash. Anything that needs understanding runs in the model. Neither does the other's job. The watcher classifies events in bash at zero token cost. Dispatch rules in config/crew-dispatch.json are natural language that the model reads; scripts only validate the JSON shape.
A restart is a non-event Nothing important lives only in chat memory. Obligations close by durable records. Append-only status logs, a durable wake queue with explicit acknowledgement, and one session-start digest that rebuilds the whole picture.
Delegation with a spine Every task gets an explicit contract before it starts. Unlanded work is never thrown away. fm-brief.sh scaffolds the contract. fm-spawn.sh refuses leftover placeholders or a mode mismatch. fm-teardown.sh refuses dirty or unlanded worktrees.
The fleet outlives any vendor Any verified agent CLI and several terminal backends can host the system. 14 harness adapters, 5 backend adapters, and one supervision recipe per primary harness in docs/supervision-protocols/.
Token budget as a design constraint

Every word in AGENTS.md is paid for on every turn. VISION sets a ceiling of 9,000 words for that always-loaded contract (it is 6,845 today), and any change that would cross it must prune or move content behind a trigger first. That single constraint explains why so much detail lives in skills and script headers instead of the main file.

§4The repository is the product

Most orchestration tools ship as an app or a service. Firstmate ships as a directory that a general-purpose agent CLI reads and executes. The README calls this an agent distro: instructions, skills, scripts, and state conventions. Clone the repo, launch a supported agent CLI inside it, and that session becomes the first mate.

Each layer has a different cost to the model, and the layout follows directly from that cost.

The layers, one by one

  • AGENTS.md is the always-loaded contract: identity, five hard rules, the task lifecycle, escalation etiquette, and an index of when to load which skill. CLAUDE.md is a two-line file that imports it, so Claude Code picks it up too. Lines of the form "Load skill when situation" are how detail gets pushed out of the always-loaded file.
  • .agents/skills/ holds 29 agent-only skills, each a SKILL.md with the procedure for one situation: landing a PR, recovering a stuck worker, provisioning a second mate. .claude/skills is a symlink to it. The separate public skills/ directory holds standalone skills meant for other projects.
  • bin/ is the deterministic toolbelt. Each script opens with a header comment that is the authoritative description of its behavior and flags. Files ending in -lib.sh are sourced libraries.
  • Harness integration files wire each agent CLI's events to scripts: .claude/settings.json, .pi/extensions, .omp/extensions, .opencode/plugins, .cursor/hooks.json, .codex/hooks.json, .grok/hooks. On Claude Code, the SessionStart hook prints the startup digest, PreToolUse hooks vet commands before they run, and Stop hooks keep supervision alive between turns.
  • Private home directories (data/, state/, config/, projects/, .env) are gitignored. The tracked repo stays a generic template while each user's fleet stays private.

Tools that live outside the repo

Firstmate leans on a handful of external CLIs, and the startup check offers to install any that are missing:

  • treehouse keeps a pool of clean git worktrees so each task gets an isolated copy.
  • no-mistakes is a validation pipeline behind a local git proxy: AI review, tests, documentation, then push and PR.
  • tmux (or Herdr, Zellij, Orca, cmux) hosts the worker terminals.
  • tasks-axi manages the backlog in data/backlog.md; gh-axi talks to GitHub; quota-axi reports model quota for dispatch; lavish-axi renders visual decision boards.
One owner per contract

The docs follow a strict rule: every contract has exactly one authoritative owner, usually a script header, and every other file points to it ("bin/fm-teardown.sh's header owns the landed-work proofs"). That is why many docs read as pointers. When two sources seem to disagree, the named owner wins.

§6Life of a task

The main path through the system is a ship task: the captain asks for a change and gets back a PR. The figure follows one task end to end, including a mid-task question from the worker.

#What happensOwner
1The captain asks in chat: "fix the flaky login test".chat
2The first mate resolves which project is meant, classifies the work as ship or scout, and fixes the delivery mode and merge posture for this task.AGENTS.md §7, fm-project-mode.sh
3It files a backlog item and scaffolds the brief, then fills two sections: Captain's intent (the human's own ask) and Firstmate spec (build instructions).fm-tasks-axi.sh, fm-brief.sh
4It picks harness, model, and effort, creates an isolated worktree and a terminal window, and launches the worker on its brief. The backlog item moves to In flight automatically.fm-dispatch-resolve.sh, fm-spawn.sh
5The worker implements on branch fm/<id> inside its worktree.worker
6It hits a judgment call, appends needs-decision [key=…]: … to its status log, and stops.state/<id>.status
7The watcher classifies the line as actionable, queues a wake, and the first mate is woken.fm-watch.sh, fm-wake-drain.sh
8The first mate decides (or escalates to the captain if the call is genuinely theirs) and answers through the worker's inbox, closing the decision with --resolve-key.fm-send.sh, skill ask-user-authority
9The worker runs the delivery path. Under no-mistakes that means AI review, tests, docs, push, PR, and CI.no-mistakes
10The worker appends done: with the PR URL. The watcher wakes the first mate, which records the PR and arms a merge poll.fm-pr-check.sh
11The first mate reports the outcome with the full PR URL, in plain language.AGENTS.md §9
12The captain says "merge it". A project with a standing yolo grant skips this step for green, in-scope work.chat
13The merge script re-reads live PR state, merges bound to the verified head commit, and confirms the merge landed.fm-pr-merge.sh
14Cleanup returns the worktree only after proving the work landed, closes the window, and moves the backlog item to Done.fm-teardown.sh

Why the brief has two halves

The Captain's intent section holds only what the human asked for, in their words. Under no-mistakes it is passed to the reviewer as acceptance criteria, so the first mate is forbidden from widening it. Its own build instructions go in Firstmate spec. Splitting them keeps a reviewer from treating the supervisor's extra ideas as requirements.

Delivery is chosen per task

ModeWhat the worker doesBuilt-in validationHow it lands
no-mistakesimplement, run the no-mistakes pipeline, open a PRAI review, tests, docs, CIPR merge under the configured merge authority
direct-PRimplement, push, open a PRCI onlyPR merge under the configured merge authority
local-onlyimplement on a branch, then stopnoneafter approval, the first mate fast-forwards local main with fm-merge-local.sh

Merge authority is a separate axis called yolo. With it off, the captain approves every merge. With it on, the first mate may merge green, in-scope work itself. Red PRs never merge under either setting, and destructive or security-sensitive merges always escalate. Each project's standing posture lives in data/projects.md. A new project with a remote defaults to no-mistakes-prod-only, a policy that sends product-facing work through no-mistakes and internal tooling through direct-PR. A project with no remote defaults to local-only.

A scout follows the same path with a different deliverable: data/<id>/report.md, no branch, no push. Its worktree is scratch. When the findings justify building something, fm-promote.sh converts the scout into a ship task in place.

§7The supervision engine

Supervision is where most of the engineering effort went. The core idea is simple: an LLM is an expensive way to wait, so waiting happens in bash. The watcher sleeps on the fleet, sorts every event into "routine" or "needs judgment", and wakes the model only for the second kind.

What wakes the first mate

WakeMeaning
signal:A worker appended a status line that needs attention, or ended its turn with no evidence it is still working.
stale:A worker's terminal stopped changing and the worker cannot be proven busy. Repeated escalations on the same pane add a count, then a demand-deep-inspection marker.
check:A registered poll fired: a PR merged, a captain inbox note arrived, a Relay mention came in, a process-event source reported.
heartbeat:A periodic backstop: review the whole fleet even if nothing reported.

Absorb only on positive evidence

The watcher swallows a quiet or turn-ended worker only when it has positive proof the worker is still running: an active no-mistakes pipeline step, or an exact "busy" verdict from that worker's harness. Missing, stale, or ambiguous evidence surfaces as a wake. The asymmetry is deliberate. A false alarm costs a few tokens; a swallowed event can strand a task for hours.

Events are separate from current state

A worker's state/<id>.status file is an append-only event log, never a state field. Current state is derived by fm-crew-state.sh from three sources: no-mistakes run records, the semantic busy state, and a fold over the status log. Reading only the last line is a known trap, because an earlier open question can be buried under later progress lines. That is why every drain prints a fleet-wide OPEN DECISIONS section computed by the fold in fm-classify-lib.sh.

"Busy" is semantic, per adapter

Each harness reports its own turn start and end through hooks or extensions it already exposes. A Claude Code worker, for example, reports through owned UserPromptSubmit, Stop, StopFailure, and SessionEnd hooks. The verdict is one of busy, idle, unknown, or dead, and unknown is never promoted to busy or idle. Scraping rendered terminal text is a quarantined fallback, used only for harnesses with no semantic source, and limited to classifying that harness's own task.

Durable queue, explicit acknowledgement

The watcher writes the queue row before it wakes anyone. The drain presents rows; the handling turn acknowledges them with the exact --ack-through command the drain printed, only after it has handled them. If the turn is interrupted halfway, the row is still there and is presented again. The design prefers a rare duplicate over a silent loss.

No turn ends blind

The model must never stop supervising while workers run, and a hook enforces it: when work is in flight and no watcher holds a fresh liveness beacon, the turn-end guard blocks the stop (or forces one follow-up on harnesses that cannot block). It is the structural backstop behind the prose rule in AGENTS.md §8.

Off the main conversation

On Pi, a second in-process conversation (the supervision branch) handles routine wakes so the captain's conversation stays clean. On a Claude Code primary, a supervision host runs the same contract as a headless session, and is on by default. Both use the same prompt, the same eligibility rules, and the same guarded scripts as the main session.

Session start rebuilds the picture

Every session begins with bin/fm-session-start.sh, which a SessionStart hook runs automatically on harnesses that support it. In order, it takes a per-home session lock, runs bootstrap diagnostics (missing tools, repairs), drains the wake queue, and prints one digest of every record above. Slow network checks run off that path and report later. The digest comes with a read-once contract: the model must not re-read the files it just printed, which saves tokens on every start. If the lock cannot be taken, the session stays read-only, so two first mates never supervise the same home.

§9Safety rails

AGENTS.md opens with five hard rules, in priority order:

  1. Never write to a project.
  2. Never merge a PR without the captain's explicit word.
  3. Never tear down unlanded work.
  4. Crewmates never address the captain.
  5. Report outcomes faithfully.

Prose rules depend on the model remembering them. Wherever a rule can be checked mechanically, a script checks it and refuses with a reason. These are the main enforcement points.

Worktree isolation

fm-spawn.sh · fm-tangle-lib.sh · fm-test-run.sh

Every worker gets its own worktree. Ship briefs open with an isolation assertion, and a spawn that cannot prove isolation stops. Workers carry FM_TASK_ID, so the test runner refuses to run in the primary checkout. A non-default branch checked out in the primary copy is flagged as a "tangle" at session start.

Spawn contract

fm-spawn.sh · fm-brief.sh · fm-dod-lib.sh

A ship spawn refuses a missing --mode or --yolo, leftover {TASK} placeholders, and a brief whose recorded Delivery contract: mode= line disagrees with the flag. The worker's instructions and the task record cannot drift apart.

Merge gate

fm-pr-merge.sh

Requires a canonical PR URL, then reads live state: open, not a draft, mergeable, every check green at the current head, every required check reported. It merges with --match-head-commit and records success only after confirming the merge landed. Gerrit changes are always refused.

Fail-closed cleanup

fm-teardown.sh

Refuses dirty worktrees and commits that have not landed. A scout's scratch worktree is released only after its report exists. --force exists, and using it requires the captain's explicit permission to discard that work.

Pre-execution hooks

fm-arm-pretool-check.sh · fm-cd-pretool-check.sh · fm-subagent-pretool-check.sh

PreToolUse hooks vet commands before they run: one polices how the watcher may be started, one guards cd, one checks the shape of sub-agent delegation. While this guide was being researched, a shell loop that merely named the watcher script was denied as unclassifiable-protected-command.

Data plane and control plane

fm-send.sh · fm-control.sh

fm-send.sh delivers text as a durable inbox record plus a short "doorbell" line typed into the terminal. fm-control.sh exposes only interrupt, exit, and relaunch. They are split because a routing-marked /quit sent as text arrives as chat that the agent reasons about instead of executing.

One more rail protects the repo's own validation: .no-mistakes.yaml sets disable_project_settings: true, which no-mistakes honors only from the trusted default-branch copy, so a pushed branch cannot rewrite the instructions used to review it.

§10Harnesses and backends

Every launch makes three independent choices, and each one is an adapter behind a small interface. That is how one codebase runs on 14 agent CLIs and 5 terminal backends without forking its logic.

  • Backends. fm-backend.sh selects a backend and dispatches operations such as capture, send key, send text and submit, and kill to bin/backends/<name>.sh. Selection order: an explicit config/backend, then runtime auto-detection ($TMUX, then HERDR_ENV=1, then cmux markers), then tmux.
  • Harnesses. Detection and model/effort resolution live in fm-harness.sh; launch flags in fm-spawn.sh; interrupt and exit keys in fm-control-lib.sh; verified facts in the harness-adapters skill. An adapter earns "verified" status through live evidence recorded under docs/verification/.
  • Primary wait shapes differ. Claude Code uses a Stop hook, Pi and omp use extensions, Codex uses bounded foreground checkpoints, Grok uses background notifications, OpenCode uses a TUI plugin, and Cursor uses a stop hook. The session-start digest prints the matching recipe from docs/supervision-protocols/.
  • Dispatch profiles. An optional config/crew-dispatch.json holds natural-language routing rules, such as which harness and model suit which kind of task. The first mate picks a profile at intake, consulting quota-axi for remaining quota, and scripts validate only the JSON shape and the harness/effort combination.

VISION sets one rule for all of this: contracts bind to semantics a vendor actually exposes. Reading a vendor's rendered screen is allowed only as a named, version-pinned adapter that is expected to break on that vendor's next release.

§11Scaling out

Second mates

A large fleet can split into domains. A second mate is a full first mate running in its own isolated home: its own state, backlog, project clones, and session lock. The main first mate routes work to it by a natural-language scope recorded in data/secondmates.md. A home can live on this machine or as a whole home on another machine reached over SSH.

Second mates are idle by default. After a restart they reconcile only work already in their own home, then wait silently; an empty queue never authorizes a self-directed survey. An unreachable remote host is treated as unknown rather than dead, so its work is never failed over to a local replacement.

An incident that shaped the design

On 2026-09-02, four outcomes from two second-mate homes never reached the captain. Each mate did the work, then reported in its own chat, which nobody reads. The fix was structural: every script that records an outcome (a PR registration, a merge, a hold for the captain) also publishes it on the parent channel. As docs/secondmate-parent-channel.md puts it, "the scripts report facts, the mate reports judgement".

Away mode

/afk records the captain's away instructions verbatim in state/.afk-contract. No parser reads those words; a supervision session reads them at each wake and acts by judgment, always through the same guarded scripts. Outcomes pile up for a return brief that is rendered from disk. Destructive, irreversible, and security-sensitive actions can never be pre-authorized by away instructions. /quiet is the stay-present variant: routine wakes stay off the main conversation while the captain keeps chatting.

Relay

With a pairing token in .env, the fleet can answer the owner's public mentions on X and Discord through a shared bot. Reversible requests go through the normal task lifecycle, with at most three follow-up replies per request inside seven days. A promised final reply is stored as a typed obligation on disk, so a restart or a compacted conversation cannot lose it. Without the token, none of this code runs.

§12How the repo ships itself

Firstmate is developed under the same discipline it imposes. Human-authored PRs to main must come through no-mistakes, and a required CI check verifies a structured attestation that the review, test, and documentation steps completed at the PR's current head.

  • Tests are plain bash. tests/ holds 241 *.test.sh suites (53 have e2e in the name). Shared fixtures in tests/lib.sh and tests/fixtures.sh build fake toolchains, so most suites run without tmux or real agents. Suites that need a real backend skip themselves and print what would enable them.
  • One runner. bin/fm-test-run.sh selects suites (by file, by family, or --changed), runs them with bounded concurrency, and times them.
  • CI lanes. .github/workflows/ci.yml runs two lint partitions with pinned shellcheck and actionlint, portable parallel and serial test shards, a real-Herdr lane, a stock macOS Bash compatibility job, repo invariants, and a coverage guard that proves the shards cover every suite.
  • Incidents become tests. VISION asks that field incidents turn into regression coverage, which is why many suites read like replays of a specific failure.
  • Conventions. One sentence per line in Markdown. Script headers are kept accurate as the behavior's owner. The README stays short and routes detail to the most specific doc; bin/fm-doc-audience-check.sh machine-checks where documentation belongs. Shared material changes load the firstmate-coding-guidelines skill first.

§13Trade-offs and FAQ

Why bash instead of a Python or Go service?
The product has to be something an agent can read, run, and change in place. Plain scripts with header contracts are inspectable by the same agent that runs them (VISION calls the system "introspectable, hot-modifiable, and self-evolving"), need no build step, and run anywhere the agent CLIs run. The cost is real: 107,726 lines of shell need heavy testing, pinned linters, and a CI job for stock macOS Bash.
Why visible terminal windows instead of headless subprocesses?
The captain can watch any worker or type into it directly, and AGENTS.md treats that direct intervention as authoritative. Terminal sessions also survive the first mate's own session, which keeps restarts cheap.
Why a git worktree per task?
Parallel tasks on one repository never collide, the user's clone stays untouched, and cleanup becomes a mechanical question ("did this branch land?") instead of a judgment call.
Why append-only status logs instead of a status field?
Appends cannot overwrite each other, several writers (the worker, and the first mate closing a decision) can share one log, and the watcher can process exactly the bytes it has not seen yet. The price is that current state must be derived, which is the job of fm-crew-state.sh and the decision fold.
Why a durable queue with explicit acknowledgement?
A model turn can be interrupted halfway through handling a wake. Writing the row first and deleting it only after an acknowledgement gives at-least-once delivery, so the worst case is a duplicate wake.
Why so many refusals?
VISION says workers are "supervised, not trusted". A script that refuses with a clear reason turns a possible silent mistake into a visible decision. In its words, "a refusal to discard is a finding, not an obstacle".
Why keep the command tree flat?
Every layer between the captain's intent and the acting agent loses fidelity and costs tokens. Depth is capped: captain, first mate, optional second mate, crew.
What does this design cost?
Density. docs/architecture.md packs many edge cases into long paragraphs, contracts are spread across single-owner script headers, and behavior differs per harness. Expect to follow pointers, starting from whichever owner a doc names.

§14Where to start reading

  1. README.md: the pitch, quick start, and built-in slash commands.
  2. VISION.md: 78 lines of principles; the reason behind nearly every refusal.
  3. AGENTS.md: the contract the first mate runs on. Sections 1, 7, and 8 carry the most weight.
  4. docs/architecture.md: the human companion to AGENTS.md. Dense, complete, best read one section at a time.
  5. docs/scripts.md: one line per script; use it as an index.
  6. The headers of bin/fm-spawn.sh and bin/fm-watch.sh: the two scripts that explain the most per line.
  7. docs/watcher-continuity.md and docs/turnend-guard.md: when you want the supervision details.
  8. Any tests/<subject>.test.sh: its header says what it pins. Run one with bin/fm-test-run.sh tests/<subject>.test.sh.
